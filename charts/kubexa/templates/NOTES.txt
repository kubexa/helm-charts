Next steps -- a successful `helm install`/`--wait` only proves every enabled
Deployment/StatefulSet became Ready. It does NOT prove telemetry is actually
flowing end to end: the consumer's `/readyz` gates on nats, writers, registry
AND consuming all reporting ok, but nothing in this cluster ever calls that
Service -- its only real consumer is the rollout wait itself, and it turns
Ready the moment those four checks pass even if zero agents have ever
connected. To confirm the pipeline is actually carrying data once an agent is
pointed at the agentserver:

  1. Agent connected: kubectl logs against the agentserver pod should show a
     handshake accepted; kubexa_gateway_handshake_rejected_total staying at 0
     is the metric form of the same check.
  2. NATS is receiving: `kubectl exec` into a nats-box pod (this chart
     bundles one) and run `nats stream info KUBEXA_TELEMETRY` -- the message
     count should be climbing, not flat.
  3. The consumer is writing: check its `/metrics` (or `kubectl logs`) for
     write errors, and confirm rows/entries are actually landing in
     Postgres/Loki/VictoriaMetrics for the cluster you connected -- a
     Ready consumer pod with an empty destination usually means the writer
     for that destination was never enabled (see the kubexa-consumer
     README's "Credentials" section for what each writer requires to turn on).

See the kubexa-apiserver, kubexa-agentserver and kubexa-consumer chart READMEs
(linked from this chart's README) for the full configuration surface of each.

The bundled Postgres is a single replica with no backup. Before this install
holds anything you would miss, read docs/ for the backup procedure.
